# Antigravity in Ustam

Antigravity is the fourth provider in the same Ustam Hub. Install a ready or saved custom team into selected registered projects with the existing preview/apply action. Each project returns its own outcome; a failed project does not claim that the other projects rolled back. Installation never starts an AI task, signs in, changes global settings, or installs Antigravity itself.

The supported surface is the `agy` CLI, with local version 1.2.16 or newer and a successful local help capability check. Missing, older, unknown, or incompatible CLIs return a reason before project files are written. A newer version must pass the same capability check. Account access and model execution are unverified. An installed legacy IDE does not establish custom-agent support; the UI shows it separately as unverified.

Native agent model tiers are `inherit`, `flash`, and `pro`. Chief and helper effort strings must be empty; no per-role effort mapping is invented. Balanced, quality, economy, quota-saver, and custom teams use these tiers. The saved maximum concurrency is one as an Ustam compatibility/policy limit. It is not a claim that Antigravity enforces a numeric native concurrency cap or a read-only chief.

Project files use `.agents/agents/ustam-antigravity-*.md`, `.agents/skills/ustam-antigravity-orchestrator/SKILL.md`, and `.agents/rules/ustam-antigravity.md`. Metadata and backup receipts live in `.antigravity/.bounded-orchestrator`; this is Ustam metadata, not an official Antigravity configuration location. The bridge lives in `.antigravity/tools`. Existing AGENTS.md, GEMINI.md, Codex skills, other providers and user customizations are preserved. An unowned collision in this namespace is refused. No deprecated IDE workflows are generated.

Antigravity combines rules from several locations. The installed rule applies only when the Antigravity owner is selected and directs it to its own provider namespace while keeping shared repository invariants. This is a prompt convention. It does not replace existing files or provide tool-schema, sandbox, permission, or chief read-only enforcement. Native agents use documented tool names, explicit role instructions, and `commandExecutionPolicy: off`; any required native permission remains under the user's control.

Preview binds the proposed team, current file bytes, the project directory device/inode identity and a five-minute expiry. The Hub and engine check that identity again before apply, including after a worker restart; an unavailable worker-bound preview must be recreated. The installed manifest also binds this identity, so copying an installation into a replacement directory cannot authorize restore or overwrite there. Apply checks the CLI again before writing, locks the provider transaction, saves a durable before/after backup, writes the finite managed file set and verifies every owned hash. Only completed steps appear as `preflight`, `backup`, `applied`, `verified` receipts. Restore validates backup integrity and current expected bytes before restoring the previous installation or removing the first installation. Verified reinstall preserves the first installation timestamp; restore restores the previous manifest. Unverified timestamps are never treated as measured usage evidence.

Symlink paths and changed or incomplete owned installations are refused. POSIX operations walk directories with descriptors and no-follow flags; Windows uses the same Python byte checks and symlink/reparse rejection, but real Windows runtime QA has not been performed. File writes and rollback compare expected bytes. A failed fsync after a successful replace/unlink is treated as a possible mutation; rollback is reported complete only after every original byte state is observed again. A conflicting user edit is retained and reported; backups remain available for inspection. A failed transaction with retained conflicts needs recovery inspection instead of automatic repair. Worktrees and transaction locks do not sandbox arbitrary user processes.

Native work follows the existing [manual Works protocol](ustam-work-protocol.md): bounded scope/criteria/ownership, independent acceptance-test-author before implementation, isolated preparation, candidate freeze, controller-observed verification, read-only review, integration recheck and human apply in Ustam. The generated bridge captures the provider, registered project and trusted runtime. Its native parser exposes no approve/answer/apply action. Source Python bridge invocation requires `-I`; the fixed POSIX wrapper and frozen worker command are also recorded in the installed skill. Project code is not imported by this bridge. A native CLI exit 0, soft denial or helper self-report cannot substitute for observed checks or human approval.

Unattended Jobs are disabled. Usage returns `status: unsupported`, an empty records list and empty totals, not a measured zero. Ustam does not scan IDE logs, follow arbitrary transcript paths, infer usage from global quota, or install an opt-in global statusline collector. CLI usage envelopes lack a verified persistent project-record source contract for this integration.

Schema and limits were checked against the official [subagent documentation](https://antigravity.google/docs/subagents/), [rules documentation](https://antigravity.google/docs/rules/), and [headless documentation](https://antigravity.google/docs/cli/headless/) on 2026-10-07. Native execution, account entitlement and legacy IDE support remain unverified; no paid model call is part of installation or these tests.
